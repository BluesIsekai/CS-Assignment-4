# SQL Injection – Authentication Bypass

## Owner : Tanishq Joshi-IIT2024152
A practical demonstration of **SQL Injection (SQLi)** using Python Flask and SQLite. This project demonstrates how improperly handled user input can manipulate SQL queries to bypass login authentication, along with a secure implementation using parameterized queries.

## Overview

SQL Injection is a web application vulnerability that occurs when untrusted user input is directly incorporated into SQL queries. Attackers can exploit this vulnerability to alter query logic and perform unauthorized database operations.

This project demonstrates:

- A vulnerable login system susceptible to SQL Injection.
- An authentication bypass using a crafted SQL payload.
- The root cause of the vulnerability.
- A secure implementation using parameterized queries.
- A comparison between vulnerable and secure query handling.

## Demonstration

### 1. Normal Authentication

The application contains two demonstration accounts:

| Username | Password | Role |
|---|---|---|
| admin | admin123 | Administrator |
| student | student123 | Student |

Using valid credentials allows normal authentication.

### 2. SQL Injection – Authentication Bypass

**Vulnerable endpoint:** `/vulnerable`

The vulnerable implementation directly inserts user input into the SQL query using Python string formatting.

Vulnerable SQL construction:

```python
query = f"""
    SELECT username, role FROM users
    WHERE username = '{username}'
    AND password = '{password}'
"""
```

Because user input is directly incorporated into the query, an attacker can manipulate its logic.

**Demonstration payload:**

Username:

```sql
' OR 1=1 -- 
```

Password:

```text
anything
```

**Expected result:** Authentication succeeds without providing the actual account password.

### 3. Root Cause Analysis

The vulnerability exists because user-controlled input is concatenated directly into an SQL statement.

The injected condition changes the original authentication logic. The `OR 1=1` expression introduces an always-true condition, while `--` comments out the remaining SQL on that line in SQLite.

As a result, the application may authenticate the attacker without validating the correct password.

## Mitigation – Parameterized Queries

**Secure endpoint:** `/secure`

The vulnerability is mitigated using parameterized queries.

Secure SQL implementation:

```python
query = """
    SELECT username, role FROM users
    WHERE username = ? AND password = ?
"""

user = conn.execute(
    query, (username, password)
).fetchone()
```

Instead of directly inserting user input into the SQL statement, placeholders (`?`) are used and the values are passed separately.

This ensures that user input is treated as data rather than executable SQL syntax.

**Expected result:** The same SQL Injection payload is rejected by the secure login implementation.

## Additional Mitigation Techniques

Other techniques that can help prevent SQL Injection include:

1. **Allow-list Input Validation:** Restrict input to expected formats and permitted values.
2. **Least-Privilege Database Access:** Give database accounts only the permissions necessary for their operations.
3. **Safe Error Handling:** Avoid exposing database errors, SQL statements, or internal implementation details to users.

## Vulnerability Comparison

| Feature | Vulnerable Implementation | Secure Implementation |
|---|---|---|
| Query construction | String formatting | Parameterized queries |
| User input handling | Directly inserted into SQL | Passed separately |
| SQL logic manipulation | Possible | Prevented for this injection |
| Authentication bypass | Vulnerable | Protected |
| Security approach | Unsafe | Recommended |
